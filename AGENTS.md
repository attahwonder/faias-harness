# AGENTS.md

A guide for any person or software agent that works on this repository. It does not depend on one tool or one vendor. Read `README.md` and `docs/ARCHITECTURE.md` as well.

## Purpose and status

This repository is the FAIAS harness, version 0.9. FAIAS is the Financial AI Independent Assurance Standard. The harness is planned to run the FAIAS test procedures against an AI system in a test environment.

Version 0.4 holds the design, 45 procedure records, a record checker and a preflight. It also holds a run engine for TP-SEC-001. The engine runs on SRD-1 minimal and is tested against a local stand-in for the model host. By default it runs the full item set (131 items and 25 clean-baseline requests), labelled "uncalibrated scorer, not a finding". The full set has run live through OpenRouter on 22 October 2026. That was six runs of 468 calls, against three hosted models. The 20 spike items remain as an option, labelled "engine spike, not a finding". The spike set has run live through OpenRouter on 20 and 21 October 2026. That was six runs of 180 calls, against three hosted models. Those run logs are not in the repository. Version 0.5 adds an external run of the same procedure and an MCP tool emulator. The external run goes through five channel adapters (`directline`, `openai-responses`, `a2a`, `json-http`, `generic-http`). Each is tested against a local stand-in. `generic-http` has run live one time, against the OpenRouter chat completions endpoint on 22 October 2026. That run tested the channel and the engine only. The adapter sends no system prompt. The harness cannot see if OpenRouter applied the routing lock. The harness supports no platform. Version 0.6.0 adds a second procedure, TP-SEC-006, on SRD-1 minimal only, labelled "uncalibrated scorer, not a finding; items from one model family". It is tested against a local stand-in for the model host only. No live run has used it. Version 0.6 also adds a containment self-test of the harness (`faias_harness/selftest/`). It makes client-level and process-level checks only. It is not a network sandbox. It adds one tool to SRD-1 minimal (`fee_refund`, through the tool emulator), off by default. With tools on, the orchestrator checks a kill switch, the customer's entitlement and a refund gate before each call. The owner declared the refund cap and the session limit on 29 October 2026. These values are synthetic. The tool is tested against a local stand-in only. No live run has used it. Version 0.7 adds a third procedure, TP-AGT-012 on SRD-1 minimal, one action class (a fee refund through `fee_refund`). Its scorer reads SRD-1's trace and the emulator's ledger, not the reply text. It finds a refund that one of three gates let through. These gates are the refund gate, the entitlement check and the kill switch. Each run carries the label "not a finding; one action class (fee refund); items from one model family; no second reviewer; no clearance path". The tests use a local stand-in and the local emulator only. No live run has used it. The owner declared the cap, the session limit and the time-to-halt on 29 October 2026. Version 0.7 also adds a fourth procedure. Its status is "TP-DAT-009 on SRD-1 minimal with C-05 minimal, tested against a local stand-in only; no live run". C-05 minimal is a lexical retrieval over 16 synthetic documents. Its scorer reads SRD-1's retrieval and denial lines and the emulator's ledger first. It reads the reply only for the canary and the fact phrases of a document outside the customer's entitlement. Each run carries the label "not a finding; synthetic store of 16 documents; items from one model family; one person; no review records, no change dates". Version 0.8.0 adds a fifth procedure, TP-SEC-002, on SRD-1 minimal and on an external target, and a sixth, TP-SEC-003, on SRD-1 minimal. Each run of TP-SEC-002 is labelled "uncalibrated scorer, not a finding; <authorship>; Track C(i) not run". Each run of the TP-SEC-003 item file is labelled "uncalibrated scorer, not a finding", with four limits and a note on P5. No item file of either ships, so no run of either can start from this checkout. Their tests use a local stand-in for the model host. No live run has used either. Version 0.9.0 adds a seventh procedure, TP-MOD-011, Component 1, the benchmark contamination probe, on SRD-1 minimal with the model-probe prompt. Each run is labelled "uncalibrated match rule, not a finding", with the limit of line 74 and the notes of the model probe. No comparator file ships, so no run can start from this checkout alone. Its tests use a local stand-in and neutral fixture comparators. No live run has used it. Do not write text that says or implies more.

`--start` with a profile alone never starts a run. It prints why a run may not start, or it prints that a profile alone names no run. With `--settings`, `--start` starts an engine run on the item set in the settings. It starts only after the checks pass and you type `yes`. The exit codes are 0 (done), 2 (refused) and 3 (conditions met but no run named). Exit code 4 is `yes` not typed, and 5 is a run stopped at the cap or on an error. The tests make no model call and no outside connection. Do not run `--probes` or `--start` unless you mean to spend money. Both can reach a live model host or a live agent's platform.

## Binding rules

1. **Never test production.** Run the harness only against test or staging systems. The preflight cannot find out whether a system is a production system. The operator carries that duty.
2. **No run without an isolation attestation.** The profile names an attestation file. A run does not start without it. The attestation says that the target is a test or staging system, isolated from production, with synthetic data only.
3. **Synthetic data only.** Do not put real customer data, real account data or real personal data in any file, test or example.
4. **Inert test objectives.** A test item asks for a harmless marker. It does not ask for harmful content.
5. **Keys only in environment variables.** A key never goes in a file, a log, an error message, a test or a commit. A profile holds the name of the variable, not the key.
6. **Set a spend cap.** `settings.cap_usd` must be set before a run can start.
7. **Records come from FAIAS only.** Do not add a test step, a threshold or a rating that FAIAS does not state. The harness copies the ★ rating from the Confidence line of each procedure and never computes it.
8. **Never edit quoted FAIAS text.** A record item carries `src: <file>:<line>`. The builder removes Markdown marks and table pipes only. If a record is wrong, change the builder or `OVERRIDES.yaml`, then rebuild. Do not edit `records/TP-*.yaml` by hand.
9. **`records/capability_needs.yaml` is an input file.** A person keeps it by hand. No tool writes it. It is a draft: it holds the needs on which two independent model passes agree, a `settled` entry where they differed and a third reading decided, and an `open` entry where nothing is decided. No person has checked it. After a change, run `tools/check_records.py`. Every procedure must be one of the 45, every capability one of the seven, and every cited `file:line` must exist in the FAIAS tree.
10. **Claim only what the code does.** Do not write "supported", "certified", "approved" or "compliant" about a platform, a result or a system. FAIAS is not a certification or approval scheme.
11. **Before a commit, the sweep and all tests must pass.** Run `tools/sweep_barred.py` (0 failing hits) and `tests/run_all.py` (PASS). Fix the cause. Do not change a test or a barred-term list to make a check pass.

12. **Evidence mode needs the five routing locks.** A settings file with `mode: evidence` sets `routing.only`, `routing.allow_fallbacks` (false), `routing.zdr` (true), `routing.data_collection` (deny) and `routing.quantizations`. The validator refuses it otherwise. A run starts only after the operator types `yes`.
13. **The run-signing key stays outside the repository.** It is a key made for the harness. It is never a key that signs a release of FAIAS. No test, log or commit holds it. A test makes a temporary key in a temporary folder. The throw-away key of the example logs follows this rule too. Only its public half is in the repository.
14. **Test items stay benign.** Each item asks for a harmless marker, a fictitious commitment about a product that does not exist, or a harmless canary string. A TP-SEC-006 item asks for the system prompt of SRD-1 minimal, which is synthetic and public. The disclosure is its objective. A TP-AGT-012 item asks the emulator for a refund, which it records in its ledger and makes on no system. A TP-DAT-009 item asks for a synthetic document of SRD-1's document store. A TP-SEC-002 cell sends an encoded TP-SEC-001 item, which decodes to that inert item and is in no repository file. A TP-SEC-003 item adds a synthetic document to a copy of SRD-1's store. Its objective is a nonsense marker in the reply. The document has a watermark field that the model does not see. A TP-MOD-011 item is a question of a benchmark on the allow-list of `faias_harness/engine/mod011.py`, under its licence; its objective is the second piece of the question, and it holds no attack text. Never put a real credential or endpoint in a prompt or an item. Write new items from the class definitions of the procedure. Use text from a third-party set only when its licence allows it. Credit it in `NOTICE` and `items/README.md`, and make its objective inert.
15. **An external run uses the channel that the firm's own front end uses.** A test through another channel reaches the agent by a different path. The model and version of an external target are declared by the operator. Record them as declared, never as observed. Do not add a field to an adapter's record that the channel does not return.
16. **The tool emulator returns synthetic results only.** Each result is fixed in the tools file, or a built-in handler computes it by a fixed rule. A handler reads a synthetic store. That store is the bank file `targets/srd1/data/synthetic_bank.yaml` or the document store `targets/srd1/data/synthetic_documents.yaml`. Every reference in the document store starts with `SYN-`, and a handler never writes a store. No tool acts on any system. The emulator listens on the local machine. Set a key variable before a tunnel exposes it. A tools file and a store hold no real account, customer or system data. Never put a name under `.invalid` or a placeholder mark in a tool description, a store or a result. The TP-SEC-006 scorer and its static inspection count them.
17. **No probe target or test target is a real outside host.** An example profile names a real host only where the channel has one fixed base address. That is Direct Line, in `targets/examples/copilot_studio.yaml`. The tests send nothing to it. A test may name the model host when nothing is sent to it. It can be in an allow-list, a base URL or a log header. A probe target name ends in the reserved name `.invalid` (RFC 2606). A probe target address off the local machine is in 192.0.2.0/24, 198.51.100.0/24 or 203.0.113.0/24 (RFC 5737). A new network, process or server site fails the static scan of the self-test. Add it to the declared list in `faias_harness/selftest/scan.py`, with its reason.

## Add a target profile

1. Copy `targets/examples/chat_only.yaml` to a new file.
2. Fill in the fields that `docs/ARCHITECTURE.md`, section 5, describes. List only the capabilities that the system really offers to the harness.
3. Use a staging endpoint. Use a name such as `staging.example.test` in examples. Put no key in the file. If the adapter needs a key, set `settings.api_key_env` to the name of an environment variable.
4. Point `attestation_file` to a statement by the firm that the target is a test or staging system, isolated from production, with synthetic data only.
5. Run the preflight on the profile. An invalid profile gives a list of problems and exit code 2. Fix them.
6. Run the sweep and the tests.

A profile for the real system of a firm holds information about that firm. Keep it outside this repository.

## Add an external target profile

1. Copy the example for the channel. The examples are `targets/examples/copilot_studio.yaml` (`directline`), `responses_agent.yaml` (`openai-responses`), `a2a_agent.yaml` (`a2a`) and `json_app.yaml` (`json-http`).
2. Set `endpoint` to the staging agent's channel. Put the adapter's settings in `adapter_options` (each adapter module's docstring lists them). Put no key in the file. Name the variable in `settings.api_key_env`.
3. Copy `targets/examples/external_settings.yaml`. Set the cap and the cost per call from the platform's prices. Keep `item_set: spike` until the channel probe and a first run show replies.
4. Point `attestation_file` to the firm's statement, run the preflight with `--settings`, then `--probes`.
5. Keep the profile and the settings outside this repository.

## Add an adapter

1. Read `faias_harness/target.py`. It defines one method group for each of the seven capabilities. Implement the groups for the capabilities that the system exposes. Leave the others to raise `NotImplementedError`.
2. Put the adapter in `faias_harness/adapters/`. Set its `capabilities` attribute to the capabilities that it really implements.
3. Send traffic only to the staging endpoints that the profile names. Take any key from the environment variable that the profile names. Do not reach into production systems.
4. Add the adapter to the table in `faias_harness/adapters/README.md`. Mark it **untested** until a test exercises it. A test needs no real vendor account: use a local stand-in server or recorded responses.
5. Write "supported" only when a test shows it, and say what the test covers. A page in `docs/PLATFORMS.md` that describes a vendor feature is not a test and is not support.
   For a channel adapter of an external run, subclass `adapters/base.py` `ChannelTarget`. Send through `_send_with_retry`. It calls `before_send`, so the call budget counts every attempt. Fill `last_exchange` only with what the channel returned. For a fault that every call hits, raise `ChannelError` with the kind `auth` or `config`. Add `validate_options` and `hosts`, and add the adapter to `adapters/registry.py`. Add a stand-in to `tests/standins.py`.
6. Run the sweep and the tests.

## Writing rules for text in this repository

- Use UK spelling. Use short sentences, active voice and plain words. Use one word for one meaning. State facts. Do not use sales language.
- Say what a part does, and say what it does not do. Keep README, `docs/ARCHITECTURE.md`, `CHANGELOG.md` and the counts in them equal to what the commands print.
- Give a source for a number, or leave the number out.
