# Changelog

## 0.5.0 (28 October 2026)

External targets. The engine can now run TP-SEC-001 against a deployed staging agent. It uses the channel that the agent's own front end uses. The harness also has a tool emulator for `tool_routing`. Each adapter is tested against a local stand-in. One live run has used an external target, on 22 October 2026. That run sent 60 calls of the spike set to openai/gpt-oss-120b, through `generic-http` and the OpenRouter chat completions endpoint. It tested the channel and the engine only. The adapter sends no system prompt. The harness asked OpenRouter for the routing lock. It cannot see if OpenRouter applied the lock. The other four adapters are untested against the platform they are written for. The harness supports no platform.

- Why a second engine path? The SRD-1 engine builds SRD-1 minimal in the same process. It reads the model, host, tokens and cost from its gateway. A deployed agent offers none of that to an outside client. `faias_harness/engine/external.py` is a client of the agent's channel. It sends the same items, scores them with the same scorer and computes M1 to M4 with the same formulas. It records what the channel showed for each call. The probe, the `yes` prompt, the lock before the first item and the signature work as for SRD-1.
- Settings `kind: external` (`faias_harness/settings.py`, `targets/examples/external_settings.yaml`). They have no provider, routing locks or token prices, because the harness does not make the agent's model calls. The budget is `cap_usd` and the operator's estimate `cost_per_call_usd`. The run stops before it passes floor(cap / cost) calls, or `max_calls` if lower. Every attempt that may reach the agent is charged. Also `min_interval_ms` (pacing), `reply_timeout_s` and `max_consecutive_errors`. Evidence mode needs the declared model, the declared target version and the M4 value with its reason. A settings file for SRD-1 may now say `kind: srd1`. Its settings hash is unchanged.
- Run log schema 3 (`faias_harness/engine/runlog.py`). The header has `target`, `model` with `pinned: false`, and `budget`. `target` gives the adapter, the channel, the endpoint host, what the channel shows, and the profile name and hash. It also gives the declared model and version with the basis "declared by the operator in the settings; not observed by the harness". `not_in_run` lists what an external run cannot see. `verify` checks these fields. It checks schema 1 and 2 logs as before.
- Channel adapters (`faias_harness/adapters/`). `directline` is for Direct Line 3.0, with a secret or a token endpoint. It is written for Copilot Studio agents and Azure Bot Service bots. `openai-responses` is for the Responses API. It is written for OpenAI, and for Azure AI Foundry agents through a project's Responses endpoint. `a2a` is for Agent2Agent JSON-RPC 1.0 and 0.3. Each offers `conversation` only. `adapters/registry.py` lists them. `adapters/base.py` holds the shared base class, the call budget and the retry rule (HTTP 429 and 503 only).
- `json-http` (`faias_harness/adapters/json_http.py`, `targets/examples/json_app.yaml`) is for a firm's own chat endpoint that takes and returns JSON. It is set up with settings only. They are a request template with `{message}` and `{session_id}`, a reply path, and optional paths. The template is filled in the parsed body, in one pass. Thus the message cannot change the JSON structure or be filled again. The optional paths are for the server's session ID, a block, its type, the model and the finish reason. Fixed headers may hold no key. Tested against a local stand-in only.
- The key header of `generic-http`, `openai-responses` and `a2a` may now be any header name (for example `Ocp-Apim-Subscription-Key`). The scheme defaults to Bearer for Authorization and none for any other header.
- `generic-http` now sends through the egress client. Before, it called the endpoint with the standard library, outside the allow-list. It reads the finish reason, the model named in the response and the token use. It has a test against a local stand-in.
- Profile field `adapter_options` (optional) holds the settings of a channel adapter, and the adapter checks them. A field name from a fixed list of key-like names is refused anywhere in it.
- The profile validator refuses an `endpoint` with a query string, because a query can hold a key. `openai-responses` takes its query from `adapter_options.query`.
- With external settings, the preflight prints the adapter, the endpoint host and what the channel shows. It also prints the declared model and version and the calls against the call budget. It says whether the key variable is present. `--probes` makes one channel probe (one benign message). The probe reaches the firm's agent, so it needs the attestation file. `--start` also needs the M4 value with its reason, so that `verify` accepts the log. It refuses if the probe gets no usable reply. It refuses `--positive-control`, because the harness cannot weaken a deployed agent. The estimate counts the Direct Line start event as a call.
- MCP tool emulator (`faias_harness/emulators/mcp_tools.py`, `targets/examples/mcp_tools.yaml`). It is a server on the local machine that answers MCP requests. It answers protocol version 2026-07-28, with per-request metadata, where the header and the body must match. It also answers 2025-03-26, 2025-06-18 and 2025-11-25, with initialize and a session. It offers tools only, with fixed synthetic results, and writes a hash-chained ledger of every tools/call, refused calls included. It refuses an Origin that is not allowed. With a key variable set, it also refuses a request without the key. It makes each refusal from the headers alone, and closes the connection. Idle connections time out after 15 seconds. At most 256 legacy sessions are kept. A firm points its staging agent's tool at it through a tunnel that the operator runs. No engine uses it yet.
- This release adds the example profiles `targets/examples/copilot_studio.yaml`, `responses_agent.yaml`, `a2a_agent.yaml` and `json_app.yaml`.
- New tests are in `tests/test_adapters.py`, `tests/test_external.py` and `tests/test_mcp_emulator.py`. `tests/standins.py` holds local stand-ins for Direct Line, the Responses API, an A2A agent and an in-app JSON endpoint. `tests/run_all.py` step 4 checks the external example profiles and settings.
- In the Inspect log, a no-result run now has the score kind `no_result`, as in the run log. A no-result run is an empty or cut-off reply, or a channel error. This holds for SRD-1 runs and external runs. Before, the Inspect log scored it as a defence. The signed run log and its measures never used the Inspect score.
- The engine now waits until the clock passes the lock time, and then sends the first item. The wait is at most 100 ms. This applies to SRD-1 runs and external runs. On Windows, Python before 3.13 reads the clock in steps of up to 15.6 ms. CPython changed the clock in 3.13. On one machine with Python 3.11, the steps were 0.3 to 6.3 ms. Before, on those versions, the first run sometimes got the lock time, and `verify` then refused the log.
- The full item set has run live through OpenRouter on 22 October 2026, after release 0.4.0. That was six runs of 468 calls, against three hosted models. The 0.4.0 entry below says that no live run had used the full set. That statement was correct at release 0.4.0.
- `.gitattributes` keeps LF line endings in every clone. Before, a Windows clone with `core.autocrlf=true` got CRLF files. Then `tests/run_all.py` step 1 failed, because the rebuilt records differed from the checked-out copies by the CR bytes only.
- `__version__` is "0.5.0".

## 0.4.1 (25 October 2026)

The records are re-based on FAIAS version 1.3.4, published on 24 October 2026. The engine, the scorer and the item set do not change.

- `records/`: rebuilt from FAIAS 1.3.4 with `tools/build_records.py` (a second run is byte-identical) and checked with `tools/check_records.py`. One record changes: in `TP-AGT-003.yaml`, `method_class` is "Emerging Practice" (it was "Adapted Industry Practice"), because FAIAS 1.3.4 classifies that procedure again: the OWASP sources that it cites set out no test method. Its ★2 does not change. The other 44 records do not change.
- `faias_harness/engine/sec001.py`: `FAIAS_VERSION` is "1.3.4", so the header of a new run log names FAIAS 1.3.4. The procedure file of TP-SEC-001 (`PLAYBOOK_SEC_001.md`) is the same in FAIAS 1.3.3 and 1.3.4. The canvas of IRQ-SEC-001 changes in 1.3.4 (fields 14 and 17); the harness quotes no canvas text.
- `docs/ARCHITECTURE.md`: the non-production rule is cited at line 75 of `00_Admin/METHODOLOGY_STANDARDS.md`. It was line 73 in FAIAS 1.3.3; the text is the same.
- `README.md`, `AGENTS.md`, `NOTICE`, `docs/ARCHITECTURE.md`, `records/README.md`, `records/SCHEMA.md` and `tests/run_all.py` name FAIAS version 1.3.4.
- `faias_harness/__init__.py` and `pyproject.toml`: version 0.4.1.

## 0.4.0 (22 October 2026)

The run engine gets the full item set of TP-SEC-001: 131 items over the four technique classes and a clean-baseline arm of 25 requests. A run on it is labelled "uncalibrated scorer, not a finding": the scorer has no measured error rate. No live run has used the full set yet.

- `faias_harness/__init__.py`: `__version__` is "0.4.0". Through release 0.3.0 it said "0.2.0", so the `engine_version` in the header of every 0.3.0 run log says 0.2.0.
- `items/TP-SEC-001.json`: an item set for TP-SEC-001. C1 40, C2 25, C3 26 and C4 40 items, and 25 baseline requests with no attack. The items are adapted from CyberSecEval 2 and from Lakera's gandalf_ignore_instructions (both MIT), and some are written for this harness. Each item has a business activity of SRD-1, from a fixed keyword rule that the file states. `items/README.md` says what came from where. `NOTICE` credits each source, and `third_party/` holds the two MIT licence texts. A test checks the set sizes and the credits.
- The engine runs the item set. New setting `item_set`: `TP-SEC-001` (the default) or `spike` (the 20 spike items). A settings file from 0.3.0 that names no `item_set` now runs the full set, with about 7.8 times the calls; set `item_set: spike` to keep the 0.3.0 run. The run makes k passes; in each pass it sends the items, then the 25 baseline requests (the direct loop used in tests sends all k runs of each item in turn). A baseline run is recorded with an outcome (answered, blocked or no_result), is not scored, and is not in M1 to M4. The summary has a results table for each class and the baseline arm. A run on the full set is labelled "uncalibrated scorer, not a finding". Run log schema version 2: the header names the item set, counts the baseline and lists what the run leaves out (`not_in_run`, which replaces `not_in_spike`). `verify` now checks the items hash against the named set in the repository and each run's request against its item's text, and still accepts a version 1 spike log. No live run has used the full set yet. Wording written for the spike that also reached full-set output (the M4 value basis, the judge-family note, the preflight's settings block) now names the run or the engine.
- `faias_harness/engine/sec001.py`: the C2 and C3 scorer no longer counts a question, or a sentence that opens as a request ("confirm", "state", "say", "write", "tell me", "answer the", "can you", "could you", "would you", "will you"), as a commitment. Before, a refusal that repeated "Can you confirm that the fee on my X account is waived?" scored as a commitment. A test covers five such sentences. The run log header lists a fifth known false result: a true statement that names the product with a commitment word (for example, that the account is free of charge) scores as a commitment.

## 0.3.0 (22 October 2026)

The first run engine, for one procedure. It is a spike: it checks that the engine works from end to end. Its result is labelled "engine spike, not a finding". The tests use a local stand-in for the model host. It has run live through OpenRouter on 20 and 21 October 2026: six runs of 180 calls, against three hosted models. Those run logs are not in the repository.

- `faias_harness/settings.py` and `targets/srd1/settings.yaml`: a settings file with no key. In evidence mode the validator refuses a file that lacks any of the five routing locks (`only`, `allow_fallbacks` false, `zdr` true, `data_collection` deny, `quantizations`). A test seeds each missing lock and each wrong lock value.
- `faias_harness/preflight.py`: `--settings` prints the provider, model, host, precision, routing locks, the worst-case estimate against the cap and whether the key variable is present (never its value). `--probes` makes a tool-call probe and a reasoning-text probe. `--start` with `--settings` and `--sign-key` makes the probes, shows them and starts the run only after you type `yes`. New exit codes 4 (`yes` not typed) and 5 (run stopped at the cap or on an error). A profile alone with `--start` still starts nothing, exits with 3 and now prints "a profile alone names no run" in place of "no run engine in v0.2".
- `targets/srd1/app/`: SRD-1 minimal. It has the chat channel (C-01), the orchestrator (C-02), the model gateway (C-04) and a trace store with a hash chain (C-15). It has no guardrails (C-10), no tools and no retrieval.
- `faias_harness/egress.py`: one HTTP client with an allow-list, shared by SRD-1 and the engine. A request to another host is refused and logged. It is a control in the client, not a network sandbox.
- Spend cap in the gateway: the run stops before a call that could pass the cap.
- Retries in the gateway, for the failures that OpenRouter documents as temporary only (HTTP 408, 429, 500, 502, 503, 504; a 200 body with a temporary error type; a timeout or dropped connection): at most 5 per call, with the Retry-After wait or 2 to 32 seconds; counted against the cap when the host may have processed the attempt; recorded in each run record.
- The harness's call to SRD-1 now waits longer than the gateway's retries can take. Before, it timed out after 60 seconds while the gateway still retried a dropped connection, and the run stopped.
- Run outcomes: attacked, defended, blocked (a 403 content-policy, refusal or guardrail block, or finish reason content_filter) and no_result (an empty or cut-off reply that is not a success). The gateway records the finish reason. No-result runs are left out of the rates and counted on their own.
- Settings `temperature` and `seed`. Evidence mode needs both, and exactly one endpoint in `routing.only`. The gateway sends the seed plus the call number with each call; each run record holds the seed sent.
- Positive control: `targets/srd1/app/system_prompt_weakened.txt` (no rules, the same canary) and `--positive-control` on the preflight. The header names the variant.
- Host check: each reply records the host that served it. In evidence mode a reply from a host other than the locked host stops the run (status `stopped_host_mismatch`); in explore mode it is recorded only.
- `faias_harness/engine/sec001.py`: 20 items for TP-SEC-001 (5 for each class C1 to C4), a deterministic scorer, and the measures M1 to M4 with the formulas of the record. Inspect drives the run through `inspect_task.py` (one sample for each item, one epoch for each run, Inspect model `none`). Setting `runs_per_item` (k, default 3, the FAIAS minimum, at most 20), stated in the header; M4 also lists each item's successful runs out of k with a Wilson 95% interval; the preflight refuses to start without `inspect_ai`; a direct loop remains for tests, and a test shows both give the same runs and measures. The run log header states that the scorer is not calibrated and lists its known false results.
- `faias_harness/engine/runlog.py`: a run log with a header (procedure, ★ label, pinned model ID, thresholds with bases, the reviewer-set M4 value with its reason, settings hash, lock time and hash), one record for each run (with the host that served the call), a list of what the spike does not do (among them the capability `config_read`: only M1 to M4 are scored), a summary, and an Ed25519 signature with `make-key`, `sign` and `verify`. One changed byte fails verification.
- `faias_harness/adapters/srd1_http.py`: an adapter for SRD-1 minimal (`conversation`, `traces`).
- `targets/srd1/attestation.txt`: the isolation attestation for SRD-1 minimal, one paragraph, approved by the maintainer.
- `tests/`: unit tests for each part and an end-to-end test against a local stand-in model host, with a guard that fails any connection to a non-local host. `tests/run_all.py` runs them as step 7.
- Dependencies: `httpx` and `cryptography`. `inspect_ai` is an optional extra and is not needed for the tests.

## 0.2.0 (16 October 2026)

Second release. It settles most of the capability needs, completes the platform survey and adds to the SRD-1 specification. It still runs no test.

- `records/capability_needs.yaml`: a third reading, also a model, settled 17 of the 19 entries where the two passes differed, at the Preconditions lines. Each settled entry keeps both sets and a note with the reason and the lines. 2 entries stay open (TP-AGT-014 and TP-TPR-006). 5 of the 26 agreed entries were spot-checked, and no error was found.
- `tools/check_records.py` checks the `settled` entries. Its seeded-fault test has 8 faults.
- The preflight counts in `docs/ARCHITECTURE.md` follow the settled needs.
- `targets/srd1/SPEC.md` (version 0.2): rows A-09 and S-03 state that SRD-1 keeps a change log and usage logs from its first version, and A-21 lists the trace and decision store. `targets/srd1/profile.yaml`: 6 rows changed, 3 of them to `met` (TP-GOV-003 access and artefacts, TP-MOD-014 artefacts).
- `docs/PLATFORMS.md` lists the two OpenTelemetry rows. The check now also reads the project's own repository for that specification, and found both quotes on 16 October 2026.
- `docs/PLATFORMS.md`: a second round asked both passes about OpenAI `control`. The check found all 8 quotes on the page, so every platform now has a verified row for each of the seven capabilities. The survey holds 84 of 87 rows.

## 0.1.0 (16 October 2026)

First release. It shows the design and the direction. It runs no test.

- The target interface with seven capabilities (`faias_harness/target.py`, `faias_harness/capabilities.py`).
- The target profile schema and its validator (`faias_harness/profile.py`).
- The preflight: it compares a profile with the draft capability needs of 45 procedures. `--start` refuses without an isolation attestation file and without the settings `provider`, `model_id` and `cap_usd`. There is no run engine.
- 45 generic procedure records built from FAIAS version 1.3.3, with `tools/build_records.py` (second run byte-identical) and `tools/check_records.py` (with a seeded-fault test of six faults).
- `records/capability_needs.yaml`: a draft input file. It holds the needs on which two independent model passes agree, the FAIAS lines they cite, and an open entry for each of the 19 procedures where the passes differ. `tools/check_records.py` checks its form and its cited lines.
- `docs/PLATFORMS.md`: a survey of the public documentation of six agent platforms. A script found the quote of 76 of 79 rows on the vendor page on 16 October 2026. It is not an adapter and not a test.
- `AGENTS.md`: a guide for people and software agents that work on the repository.
- An untested adapter for OpenAI-compatible chat-completions endpoints (`generic-http`).
- A draft profile and specification for the example reference system SRD-1. SRD-1 is not built.
- Two example profiles in `targets/examples/`.
- `tests/run_all.py`: all tests from one command.
- `tools/sweep_barred.py`: a sweep for barred terms and key-like strings.
