# Changelog

## 0.9.6 (9 November 2026 — date of the push)

This release pins one more package in the CI job that installs inspect_ai. A new version of a package that inspect_ai needs made each engine run on Inspect fail at its start. The code does not change.

- **The CI job with inspect_ai.** The job `run-all-inspect` of `.github/workflows/tests.yml` now installs `agent-client-protocol==0.12.1` with inspect_ai 0.3.281. inspect_ai 0.3.281 accepts any version of agent-client-protocol from 0.12.0. Version 1.0.0 of agent-client-protocol came out on 9 November 2026. It has no module `acp.helpers`. inspect_ai imports that module each time it runs an eval (`inspect_ai/agent/_acp/event_mapping.py`). So each engine run on Inspect stopped with `ModuleNotFoundError: No module named 'acp.helpers'`, before any item ran. In that job the containment self-test gave FAIL, because its probe S14 runs one item on Inspect. The tests that need a passing self-test or that run an engine on Inspect failed too. The job failed in each run of the 0.9.5 push. The four jobs without inspect_ai passed. With agent-client-protocol 0.12.1 and the other packages of that job unchanged, the full suite passes. `tests/test_workflow.py` now checks the two pins of that job. `README.md` and `AGENTS.md` now name the pin and tell a user of inspect_ai to install it. The upstream report is issue 6417 of UKGovernmentBEIS/inspect_ai. Where inspect_ai is not installed, nothing changes.
- **The hashes.** The version string in `faias_harness/__init__.py` changes. So the code manifest of the containment self-test changes, and a gated run needs a self-test of this code. The two example logs in `examples/logs/` were made again at the 0.9.6 code with a new throw-away key. No file that they record changes, so the file hashes that they record do not change. No procedure, setting or log schema changes.
- **Gaps that remain.** The three gaps in the last entry of the 0.9.5 section remain. They are the form of the `fee_refund` store, the containment times of TP-AGT-012, and the field types of the M4 baseline log. Also, the harness picks the engine on Inspect whenever inspect_ai can be found. It does not check that inspect_ai can run an eval. So with agent-client-protocol 1.0.0 installed, an engine run on Inspect still fails at its start. The pin must change when inspect_ai fixes its version range.

## 0.9.5 (9 November 2026)

This release closes seven gaps in the last entry of the 0.9.4 section. It also closes five more gaps of the same kind. A run record now takes its time from the lock time and a steady clock. So a system clock that moves back no longer makes `verify` fail a log. A firm-values file or a risk-appetite file that is not a mapping now gets a refusal line. So does a date in the risk-appetite file that is not in quotes. A tools file that changes after the preflight now gives one `Run refused:` line. The preflight of TP-DAT-009 now reads the synthetic bank and the synthetic documents with the reader of the engine. An M4 baseline log that holds a lone surrogate is now refused. A write of `tools/mod011_overlap.py` that fails now leaves no file. An M4 baseline log with a line that is not a JSON object is now refused. The reader of the TP-DAT-009 data files now checks the form of both files. A refund cap or limit that is not a number now gets one refusal line at `--start` of TP-AGT-012. A temporary file that the overlap tool cannot remove after a good move now gives a note, not a refusal. A new CI job runs the tests with inspect_ai installed. Some gaps remain. The last entry lists them.

- **The time of a run record.** Each engine and the self-test now read the system clock once, at the lock, for the lock time. They also read a steady clock there (`time.monotonic_ns`), which only counts forward. Each record after the lock takes the lock time plus the steady time since the lock (`runlog.run_clock`). This holds for `t_ns` and `time` of each record. It also holds for the time in the `escalated` text of a `bypass` or `crossing` record. It holds for `finished` of the summary too. So each record is later than the lock time and not earlier than the record before it. The system clock does not change this. The time of a record is thus not the system time of the call. `verify` keeps its strict check. A run record that is not later than the lock time still fails it. The log schema and the canonical form do not change, so earlier logs verify as before. The times in `egress.jsonl`, the tool ledger and the SRD-1 trace stay on the system clock. So do their copies in a record. Before, each record took its time from the system clock. If the system clock moved back during a run, to the lock time or earlier, `verify` failed the log. Nobody had changed that log.
- **A value file that is not a mapping.** Two readers now check the type of the top level of their file. They are `profile.read_firm_values` for the firm-values file and `gate.read_risk_appetite` for the SRD-1 risk-appetite file. The first reader also checks the value of `values`. The second reader also checks the value of `fee_refund`. Such a value that is present and is not a mapping gives one problem. Examples are `firm_values.yaml: the top level is not a mapping` and `risk_appetite.yaml: the value of 'fee_refund' is not a mapping`. A text, a list, 0, an empty text and an empty list are refused. An empty file and a null value read as an empty mapping, as before. The preflight prints the refusal in the form of the other refusals of that file. `--start` of a run that reads the file refuses in that one problem line, before any model call. Before, a list or a text stopped the preflight with `AttributeError`. A value of 0, an empty text or an empty list read as an empty mapping.
- **A date in the risk-appetite file.** The reader of the risk-appetite file now checks the type of `declared_by` and `declared_on`. It refuses a value that is present, not null and not a text. An example is `declared_on: 2026-10-29` with no quotes, which YAML reads as a date. A time and a number are refused too. The problem is `risk_appetite.yaml: the value of 'declared_on' is not a text; put the value in quotes`. The runs that read the refund gate get the check. These are TP-AGT-012, and TP-SEC-001 or TP-SEC-006 with tools on. The preflight prints the refusal under the tools line. `--start` refuses in that one problem line, before any model call. The TP-AGT-012 engine refuses the run before the lock. Before, such a value passed the preflight and `--start`. The TP-AGT-012 engine copies the value into its header, and the canonical form of the header cannot hold a date. So the engine stopped with `TypeError` after the typed `yes`.
- **A refund cap or limit that is not a number.** The preflight of TP-AGT-012 runs an item-set check before any model call. That check compares the fees of the items with the refund cap and the session limit of the risk-appetite file. The preflight now makes this check only when `gate.declared_problems` finds both values declared, as numbers above 0. A value of another type, for example `cap_gbp: twenty-five`, gives the line `refund cap not declared (targets/srd1/risk_appetite.yaml): SRD-1 does not enable its tool`, as before. The preflight prints it under the tools line. `--start` now refuses in that one problem line, before any model call. If the file changes after the preflight, the TP-AGT-012 engine refuses such a value before the lock, as before (`gate.RefundGate.from_file`). `--start` then prints one `Run refused:` line. A null cap or limit gives the same line. The preflight now leaves out the item-set check for it too. Before, a value of another type stopped `--start` with `TypeError` in the item-set check. With a null value, the check ran without the rules that need that value.
- **A tools file that changes after the preflight.** A run that serves the tools file reads it again when it starts the tool emulator. That read comes after the typed `yes` and before the lock. These runs are TP-AGT-012, TP-DAT-009, and TP-SEC-001 or TP-SEC-006 with tools on. When the emulator refuses the file, the engine now raises a `ValueError` with the problem line of the preflight (`toolrun.ToolRun`). An example is `TP-AGT-012: the tool emulator file targets/srd1/tools.yaml is refused: <reason>`. So `--start` prints one `Run refused:` line and the run folder, and exits with 2. The engine sends no request and opens no run log. The rule for a `Run refused:` line does not change. Before, `--start` stopped with a traceback of `mcp_tools.ToolsError`.
- **The data files of TP-DAT-009.** The TP-DAT-009 engine reads the synthetic bank and the synthetic documents with its own reader (`dat009.load_data`). That reader now refuses each of three faults in one problem. These are a lone surrogate, a file that is not UTF-8 YAML and a file that cannot be read. An example is `synthetic_bank.yaml holds a lone surrogate in the key or the value of 'domain'`. It also refuses a store file whose `documents` value is not a list. It now checks the form of the two files too. The form is the one that the engine, the scorer, SRD-1 and the tool emulator read with no default (`dat009._form_problem`). The bank must be a mapping. Its `customers` must be a list of mappings with `customer_ref` and `domain` as texts. Its `accounts` must be a list of mappings with `customer_ref` and `account_ref` as texts. Its `default_customer_ref` must be a text that names a customer. The list `documents` must not be empty. Each document must be a mapping with `doc_id`, `title`, `text`, `domain`, `kind` and `canary` as texts. Its `customer_ref` must be present, as a text or null. Its `facts` must be a list of texts. The documents file must also hold a list `customers` of the form of the bank's list. The tool emulator reads that list as the entitlement table of the store. Each fault gives one problem, for example `synthetic_bank.yaml: the value of 'customers' is not a list`. The preflight of TP-DAT-009 now reads the two files with this reader. It prints `Data files: a file is refused: <problem>`, and no estimate. `--start` refuses in one problem line, `TP-DAT-009: a data file is refused: <problem>`, before any model call. The documents are also the store of the tools file. A fault that the reader of the tools file finds in the documents is named once. It is named as a refused tool emulator file. Before, the preflight did not read the bank. With the pure-Python YAML loader, a lone surrogate in the bank reached the matrix of the run (evidence output E1). A bank that was not UTF-8, or that was absent, passed the preflight and `--start`. The engine then stopped after the typed `yes`. A bank of another form passed the preflight and `--start` too. An example is a `customers` value that is a text. The engine then stopped with `TypeError` when it made the matrix, after the typed `yes`. A `documents` list with a value that is not a mapping stopped the preflight with `TypeError` at the estimate. A document with no `title` stopped it there with `KeyError`.
- **An M4 baseline log with a lone surrogate.** The reader of the M4 baseline log of TP-SEC-006 (`sec006_log.read_baseline`) now refuses a log that holds a lone surrogate. The one problem names the key, for example `the M4 baseline log holds a lone surrogate in the key or the value of 'time'`. The reader makes this check before the check of the signature, so with or without `m4_baseline_pubkey`. The TP-SEC-002 reader of its baseline (`sec002_log.read_baseline`) reads the log through this reader. So it refuses such a log too, with `the baseline log holds a lone surrogate in the key or the value of '<key>'`. The preflight prints the problem, and `--start` refuses in that one line, before the typed `yes`. Each engine refuses such a log before any model call. Before, the preflight and `--start` passed such a log with no key. They also passed it with a key when the log was signed after the edit. The TP-SEC-006 engine then stopped with `UnicodeEncodeError` before the first item when its header copied the text. Otherwise it ran the whole set.
- **An M4 baseline log with a line that is not a JSON object.** The reader of the M4 baseline log now refuses a line that is a JSON value but not an object. Examples are a list, a text, a number and null. The one problem names the first such line in the file, for example `the M4 baseline log line 2 is not a JSON object`. A blank line counts in the number. The TP-SEC-002 reader of its baseline reads the log through this reader. So it refuses such a log too, with `the baseline log line <n> is not a JSON object`. The preflight prints the problem, and `--start` refuses in that one line, before the typed `yes`. Before, a first or a last such line stopped both readers with `AttributeError`. So the preflight stopped with a traceback. With `m4_baseline_pubkey`, a line between them stopped both readers in the check of the signature, with `AttributeError`. With no key, such a line passed the reader of TP-SEC-006, its preflight and `--start`. The TP-SEC-002 reader then stopped with `AttributeError` when it scored the log again.
- **The write of the overlap tool.** `tools/mod011_overlap.py` now writes the result to a new temporary file in the folder of `--out`. That file then becomes `--out` only while `--out` does not exist. On POSIX the move is a hard link, and on Windows it is a rename. A write that fails leaves no file at `--out`, and the tool removes the temporary file. The line is `refused: <out> cannot be written (<reason>)` (exit 2). The tool never overwrites a file. An `--out` file that another process makes while the tool runs keeps its bytes. The line is then `refused: <out> exists` (exit 2). On POSIX the result file can be read and written by its owner only, as for each temporary file. A file system with no hard links cannot take the result on POSIX, and the tool refuses the write. After the hard link, the temporary file is a second name of the result, and the tool removes it. If the system does not let the tool remove it, the result stays at `--out`. The tool then prints the line of a written result and one note line, `note: the temporary file <path> cannot be removed (<reason>)`. The exit code is that of the result. Before, a write that failed part way left a part of the result at `--out`. A second run then refused that path, because it existed. A file that another process made at `--out` while the tool ran was overwritten.
- **The tests of the Inspect path.** The workflow `.github/workflows/tests.yml` has a new job, `run-all-inspect`. It runs `tests/run_all.py` on Linux with Python 3.14, with inspect_ai 0.3.281 installed. Where inspect_ai is installed, some engine tests run the engines on Inspect, not on the direct loop. Some tests compare the two engines. Without inspect_ai, they print a note and check nothing. The pin does not fix the packages that inspect_ai needs. So a new version of one of them can change the result of this job. The four jobs without inspect_ai do not change. Also, two tests now hold on Inspect too. Inspect runs run 1 of every item before run 2. The direct loop runs the runs of each item in turn. The TP-SEC-002 test in `tests/test_external.py` now compares the outcomes in the order of item and run. The cost-cap test of TP-MOD-011 now expects the stop record of the engine in use. Before, no job of the workflow installed inspect_ai. So the tests of the Inspect path ran only where a user had installed it. There, these two tests failed, because each test took the order of the direct loop. The engines did not cause the failures.
- **The hashes.** The code manifest of the containment self-test changes, so a gated run needs a self-test of this code. New TP-AGT-012 run logs record a new SHA-256 of `targets/srd1/app/gate.py` (`structural_inspection.module_sha256`). New TP-DAT-009 run logs record a new SHA-256 of `faias_harness/engine/dat009.py` (`code.scorer_sha256`). `verify` does not compare these hashes with the checkout, so this change does not fail an earlier log. For an earlier TP-DAT-009 log, `rescore` says that the scorer in the log differs from the scorer used. The two example logs in `examples/logs/` were made again at the 0.9.5 code with a new throw-away key. No file that they record changes, so the file hashes that they record do not change. No procedure, setting or log schema changes.
- **Gaps that remain.** The tool emulator reads the synthetic bank as the store of the `fee_refund` tool (`handlers.load_store`). That reader does not check the form of the accounts and their fees. TP-AGT-012 reads that store, and so do TP-SEC-001 and TP-SEC-006 with tools on. An example is an entry of `accounts` that is not a mapping. With such a store, `--start` of TP-AGT-012 stops with `AttributeError` in the item-set check, before any model call. TP-SEC-001 and TP-SEC-006 pass the preflight and `--start`. The tool emulator then stops with `AttributeError` when it starts, after the typed `yes`. Also, the containment times of TP-AGT-012 come from the SRD-1 trace and the tool ledger, on the system clock. A step of the system clock during a containment run changes them. No check of `verify` compares them with the lock time. Also, the reader of the M4 baseline log does not check the type of the fields that it reads in the header and the summary. An example is a header whose `procedure` is a text. Such a log stops the preflight and `--start` of TP-SEC-006 and TP-SEC-002 with `AttributeError`, not with a refusal line.

## 0.9.4 (8 November 2026)

This release closes four gaps in the last entry of the 0.9.3 section. A lone surrogate in a reply no longer stops a run. A lone surrogate in printed text no longer stops a command. A changed copy of four item files gets a refusal line. A channel error message keeps a code from the target only in a fixed form. Two tests read `egress.jsonl` of the run folder. A file of the operator that holds a lone surrogate now gets a refusal of one line. Two more tests pin two of these claims. A request to the tool emulator that holds a lone surrogate now gets its response. An item file that is not found no longer stops the preflight. The other YAML files of the operator now refuse a lone surrogate too. So does the risk-appetite file of SRD-1. An absent firm-values file now gets a refusal line. Some gaps remain. The last entry lists them.

- **A lone surrogate in a reply.** A reply can hold a lone surrogate, for example the JSON escape `\ud83d` alone. Python reads it as one code point from U+D800 to U+DFFF, and such a text cannot be written as UTF-8. The harness now replaces each lone surrogate with U+FFFD (the Unicode replacement character) where a reply enters. The first point is the body of a channel response (`ChannelTarget._json`, which the five channel adapters use). The second is the body of a model host response (SRD-1's gateway). The third is the tool arguments that SRD-1's orchestrator reads from a model reply. So the probes, the external engine and each SRD-1 engine see U+FFFD. The canonical form of a log line does not change, so earlier logs verify as before. Before, such a reply stopped an external run after the lock, with an unsigned log. With `store_replies: hash_only`, a probe reply stopped `--probes` and `--start` before the typed `yes`. With `full`, it stopped the run at the header, after the typed `yes`. On SRD-1, the write of the trace line failed, so SRD-1 answered HTTP 502.
- **A lone surrogate in printed text.** A file of the operator can hold a lone surrogate too. Each command now prints such a character as an escape, for example `\ud83d`, and does not stop with a traceback. The commands are the preflight, `runlog`, `selftest`, `testability`, the tool emulator, the TP-SEC-002 item tool and each script in `tools/`. Each sets stdout and stderr to `errors="backslashreplace"` first (`faias_harness/text.py`). For example, the preflight prints a profile path that holds a lone surrogate with the escape, and exits with 2. A lone surrogate in the text of a file of the operator now gets a refusal (the next entry).
- **A lone surrogate in a file of the operator.** Each JSON reader that refuses a repeated key now refuses a lone surrogate too (`jsonkeys.unique_keys`). The lone surrogate can be in a key or in a text value. The one problem is `a JSON object holds a lone surrogate in the key or the value of '<key>'`. The files are the TP-SEC-002 item file (for the engine and the item tool) and the TP-SEC-003 item file. They are also the TP-MOD-011 comparator file and overlap result, and the item and instrument files that ship. The refusal has the form of the refusal of a repeated key. So the preflight prints that the file is refused and gives no estimate. `--start` refuses in one problem line, before any model call. A surrogate pair, for example the JSON escapes of an emoji, reads as one character and passes. So does U+FFFD. Before, each reader passed such a file. For a TP-SEC-003 document, the loader now refuses the file before the item check names the key.
- **Three commands.** `mcp_tools verify` now names a ledger line that holds a lone surrogate. The line is `FAIL: line <n>: the line holds a lone surrogate, so its hash cannot be checked`. The exit code is 1, as for its other problems. The TP-SEC-002 item tool refuses such an item file in one line, with `fill-activity` and with `check`. The exit code is 1, as for its other refusals. `tools/mod011_overlap.py` refuses such a comparator file in one line (exit 2). No command writes a file. Before, `verify`, `fill-activity` and the overlap tool stopped with `UnicodeEncodeError` when they hashed or wrote the text.
- **The settings file and the profile.** Where libyaml is absent, the harness reads YAML with the pure-Python loader. That loader reads the YAML escape `\ud83d` as a lone surrogate. libyaml refuses it. The loaders of the settings file and the profile now refuse a lone surrogate. The one problem is `a YAML mapping holds a lone surrogate in the key or the value of '<key>'`. They also refuse a file that is not UTF-8, with `cannot read <file>: ...`. Before, with the pure-Python loader, a settings value stopped the preflight with a traceback at the settings hash. A profile value reached the lock of the run header after the typed `yes`. `--start` then printed `Run refused:` with the error of the encoder. A file that is not UTF-8 stopped the preflight with `UnicodeDecodeError`, with each loader.
- **An item file that its loader refuses.** The preflight of TP-SEC-001 (on its full set), TP-SEC-006, TP-AGT-012 and TP-DAT-009 now reads the item file with the loader of the engine, with or without the prices. A changed copy that its loader refuses now gets the form of TP-SEC-002 and TP-SEC-003. An example is a JSON object with a repeated key. The settings block prints `Item file: <path> is refused: <reason>` and no estimate. `--start` refuses in one problem line, `<procedure>: the item file <path> is refused: <reason>`, before any model call. Before, the estimate raised the refusal of the loader, and the preflight stopped with a traceback. Also, with no item file, the estimate line of TP-AGT-012 now says "the item file is not found". Before, it said "the item file is refused" when the TP-SEC-003 item file was present. The other three procedures now give that line too (the entry "An item file that is not found").
- **A code in a channel error.** Two messages held a code from the target's body. These are the A2A JSON-RPC error code and the Direct Line error code. A message goes into the probe record, the call records of the session check and the printed probe line. The A2A message now keeps the code only when it is an integer. The Direct Line message keeps it only when it matches `[A-Za-z][A-Za-z0-9_.-]{0,63}`. Otherwise the message says that the code has another form, and holds none of it. A Direct Line error that is not an object no longer stops the adapter with `AttributeError`.
- **The egress file.** Two new tests read `egress.jsonl` of the run folder. After a TP-MOD-011 run, it holds the requests of the instrument check before the lock. After a TP-AGT-012 run, it holds the requests of the switch check before the lock. The code of the engines does not change. Before, no test read the file for these requests. So a change that sent the instrument check through a second client passed every test.
- **Two tests of two claims.** One test reads the rule for a Direct Line `error` that is not an object. One test reads the estimate line of TP-AGT-012 with no item file and a TP-SEC-003 item file present. Before, no test failed when either rule was taken out.
- **A request to the tool emulator.** The target sends each request to the MCP tool emulator from model output. So the emulator now reads a request as the harness reads a reply. Each lone surrogate becomes U+FFFD at entry (`text.clean`). A `tools/call` whose arguments hold one gets its usual response. Its ledger line holds U+FFFD, and `verify` passes. Before, the ledger failed to write the line. The call got no response, and the server printed a traceback.
- **An item file that is not found.** The prices can be set while an item file is not found. The estimate of TP-SEC-001 (full set), TP-SEC-006 and TP-DAT-009 is then not available, as for TP-AGT-012. The estimate line says "the item file is not found". `--start` refuses in one problem line, `the item file <path> is not found`, before any model call. Before, the preflight of these three procedures stopped with `FileNotFoundError` when it made the estimate.
- **The other YAML files of the operator.** Four more YAML files now refuse a lone surrogate and a file that is not UTF-8. Three are the firm-values file, the tools file and the store of the tool emulator. The fourth is the TP-SEC-002 declaration of the channel inputs. Each refusal is one problem in the form of the other refusals of that file. For a lone surrogate, the problem names the file and the key, for example `the store holds a lone surrogate in the key or the value of '<key>'`. The preflight prints the refusal. `--start` of a run that reads the file refuses in one problem line, before any model call. A run that serves the tools file gets the check of the tools file and its store. These runs are TP-AGT-012, TP-DAT-009, and TP-SEC-001 or TP-SEC-006 with tools on. The settings block then prints `Tool emulator file: <path> is refused: <reason>` and no estimate. The table prints `Firm values: the file is refused: <reason>`. The preflight of TP-AGT-012 now also runs the check of the time-to-halt that the engine runs before the lock. So `--start` now stops before the probes when the check refuses the firm-values file. It also stops there when the two values of the time-to-halt differ. `mcp_tools serve` refuses a tools file that is not UTF-8 in one line. Before, the pure-Python loader passed a lone surrogate. A file that is not UTF-8, or an escape that libyaml refuses, stopped the preflight with a traceback. A tools file that is not UTF-8 stopped the tool emulator with `UnicodeDecodeError`.
- **The risk-appetite file and an absent firm-values file.** The refund gate of SRD-1 reads its values from `targets/srd1/risk_appetite.yaml`. One reader of that file now checks it (`gate.read_risk_appetite`). It refuses a lone surrogate and a file that is not UTF-8. It also refuses a file that cannot be read, such as an absent file. The one problem has the form of the firm-values file, for example `risk_appetite.yaml holds a lone surrogate in the key or the value of 'declared_by'`. The runs that read the refund gate get the check. These are TP-AGT-012, and TP-SEC-001 or TP-SEC-006 with tools on. The preflight prints `the risk-appetite file targets/srd1/risk_appetite.yaml is refused: <reason>` under the tools line. `--start` refuses in that one problem line, before any model call. The TP-AGT-012 engine reads the file with the same reader before the lock. The header copies `declared_by` and `declared_on` from that read. The reader of the firm-values file now also refuses a file that cannot be read. So `--start` of TP-AGT-012 with no firm-values file refuses in one problem line, `cannot read firm_values.yaml: FileNotFoundError`. Before, the pure-Python loader passed a lone surrogate in the risk-appetite file. The lone surrogate then reached the header after the typed `yes`. An escape that libyaml refuses stopped the preflight with a traceback. So did a file that is not UTF-8, or an absent file. An absent firm-values file stopped `--start` with `FileNotFoundError`. - **The docs.** Section 8 of `docs/ARCHITECTURE.md` names the parts of the SRD-1 adapter that the engines use. Among them are the configuration kind `session` and the kill switch. The layout table of `AGENTS.md` names `text.py`, and gives the full scope of `jsonkeys.py`.

New TP-SEC-006 run logs record a new SHA-256 of `tools/sweep_barred.py` (`static_inspection.patterns_sha256`). - **Gaps that remain.** Each run record takes its time from the system clock. `verify` needs each run time to be later than the lock time. They are `standard text encoding`, `character substitution`, `reversed text`, `spaced letters` and `wide letters`. Each has an encoder and a decoder, and the decoder gives back the text. The Base64 encoder uses the standard alphabet, with padding. Character substitution maps the 52 ASCII letters to the Mathematical Bold letters (U+1D400 to U+1D433). Spaced letters puts one space between each pair of adjacent characters, and its decoder keeps every other character. Wide letters maps each ASCII character from `!` to `~` to its fullwidth form. `views` gives the decoded view of a reply under each family, then its NFKC view (see below). The Base64 view decodes each run of 14 or more Base64 characters at its four alignments. It reads the bytes as UTF-8, and a byte that is not valid UTF-8 becomes U+FFFD. It puts one decoded text on each line. It also pads and decodes a last group of 2 or 3 characters. It can join two runs that one space separates (see below). The floor of 14 is the length of the shortest C1 marker in Base64, padding left out. The redaction keeps its floor of 32. A measurement before the change found no chance hit from the lower floor. Its texts named no C2 or C3 product, so it covers the C1 and C4 keys only. The chance rate of a C2 or C3 commitment is not known. It used the replies of the tests, the stand-ins and the project's run logs. The spaced view reads the characters at the even places, then the characters at the odd places. The module imports no other module of the harness. It holds its own copy of the Base64 run rule of `sec006.py`, and a test checks that the two agree. `VIEW_LIMITS` states a limit of the wide letters view. It maps a fullwidth full stop, question mark or exclamation mark (U+FF0E, U+FF1F, U+FF01) to its ASCII form. Such a mark between a hedge and the restated request can split a hedged sentence. The request can then hit as a commitment.

They cover the egress client, the SRD-1 gateway, the six adapters and the two local servers. They also cover SRD-1's tool client, tool round and kill switch, the engine, git and publication. Each target name ends in the reserved top-level name `.invalid` (RFC 2606). Each target address off the local machine is in 192.0.2.0/24, 198.51.100.0/24 or 203.0.113.0/24 (RFC 5737). The command needs no key and no model, and it calls no outside host.
- There are four layers. The first is the allow-list of the egress client. The second is a mock transport that records each request and sends nothing. The third is a guard below the client (`selftest/guard.py`) for socket connect, lookup and send, and process start. The fourth is the reserved targets. The guard records and refuses every call that is not on the local machine. It allows `git -C <folder> rev-parse` and the three git commands that Inspect AI runs.
- A static scan (`selftest/scan.py`) compares every network, process and server site in `faias_harness/`, `targets/` and `tools/sweep_barred.py` with a declared list. A new site fails the self-test until it is declared with its reason. The scan also writes the code manifest, the SHA-256 of each scanned file.
- The log (schema `faias-harness-selftest-log/1`) is in the frame of a run log. It has a header, a lock before the first probe, one record for each probe and a summary. `runlog verify` checks its signature and form, also with `--no-repo`. `selftest rerun --log` runs the probes again and prints each difference (exit 1 on a difference). The summary maps the results to the steps and measures of TP-AGT-014, and `not_in_run` lists what it does not cover.
- The publication channel is recorded as "structurally absent in this version; a tool that publishes would add a path and a probe". This is how the harness reads `PLAYBOOK_AGT_014.md`, line 55. The maintainer has not yet confirmed it.
- `docs/HARNESS_ATTESTATION.md` is the maintainer's attestation of the harness. It is a draft for the maintainer's approval. The self-test refuses to run without it and records its SHA-256.
- With an SRD-1 settings file, the preflight prints one line about the newest self-test log. It looks in `--selftest-log`, in the folders of `FAIAS_HARNESS_RUNS`, or in `runs/`. `--start` refuses TP-AGT-012 and TP-DAT-009 without a verified log of this code that shows PASS. Neither has an engine yet.
- The preflight checks the signature of the self-test log against a public key file. `--selftest-pubkey` or the setting `selftest_pubkey` names it. With neither, it uses the key in the log's own `.sig` file, and the line says "(key not pinned)". That check shows that the log is whole, not who signed it. In evidence mode, `--start` also refuses TP-AGT-012 and TP-DAT-009 when the key is not pinned. The setting enters the settings hash only when it is set.

One tool in SRD-1 minimal, off by default. It is tested against a local stand-in for the model host and the local emulator only. No live run has used it.

- The emulator gains built-in handlers (`faias_harness/emulators/handlers.py`). A tool can give `result: {handler: fee_refund}` and the tools file `store: <file>`. The handler reads the store once and never writes it. It records a refund of a known fee at its amount, with a new reference. It rejects an unknown account or fee, or another amount. It checks no cap and no entitlement. tools/list sends `title`, `annotations` and `outputSchema`. A handler result carries `structuredContent`. The field names are from version 2025-06-18 of the MCP specification. The sources are the tools page (<https://modelcontextprotocol.io/specification/2025-06-18/server/tools>) and the schema (<https://modelcontextprotocol.io/specification/2025-06-18/schema>), read 28 Oct 2026. A handler call's ledger line adds the status and the refund reference. `serve --store` names another store. `targets/examples/mcp_tools_store.yaml` shows the form, and `targets/examples/mcp_tools.yaml` keeps its three fixed tools.
- SRD-1 gains `tools.yaml`, with `fee_refund` and its four annotations. `data/synthetic_bank.yaml` has 4 customers, 6 accounts and 10 fees, and every reference starts with `SYN-`. `risk_appetite.yaml` has the refund cap, the session limit and the time-to-halt objective. Each value is null until the owner declares it.
- SRD-1's orchestrator gains a tool loop, with at most 3 rounds in a turn. Before each MCP call, it checks the kill switch (C-18), the entitlement (C-07, `entitlements.py`) and the refund gate (C-09, `gate.py`). Each decision writes a `tool_call` trace line. A denial writes `entitlement_denial`, a hold writes `gate_hold`. The MCP client (`mcp_client.py`) goes through the egress client. With a null cap or limit, SRD-1 does not enable its tool ("refund cap not declared").
- The refund gate holds an amount that is not a finite number (NaN or an infinity). It also holds an amount of zero or less. It holds an integer too large for a float as above the cap, and the turn writes its `tool_call` line. The orchestrator gives `bad_arguments` for arguments that hold NaN or Infinity. It does the same for a number such as 1e400, which reads as an infinity. The handler `fee_refund` rejects the same amounts. The emulator answers a body that holds NaN, Infinity or such a number with HTTP 400 and error -32700. It writes no ledger line for it. The trace store and the ledger write JSON as RFC 8259 defines it. Their checks fail a file that holds NaN, Infinity or such a number. The emulator refuses a store whose fee amount is not a finite number above zero.
- The emulator reads and drops a refused body before it closes the connection. It does not parse the body. Before, the close could reset the connection on Windows, and the client then lost the refusal. The containment self-test saw this as a rare failure of one probe. The read stops after 2 seconds in total, so the close can reset the connection of a slow client.
- SRD-1's channel gains POST `/control/kill_switch`, GET `/config/tools`, `/config/gate` and `/config/entitlements`, and an optional `customer_ref` for POST `/sessions`. `srd1-http` offers `tool_routing` and `control` in part. Without tools, a session acts for the default customer and nothing else changes.
- New settings `tools_enabled` (default false) and `tool_key_env`. They enter the settings hash only when tools are on, so every earlier settings file keeps its hash. With tools on, the TP-SEC-001 engine starts the emulator (`engine/toolrun.py`). It generates the emulator's key in the run and keeps it in memory. The header gains a `tools` block. The lock covers it only when it is present. So the signed logs of 20 to 22 October 2026 verify as before. The summary gains `tool_ledger`. The estimate counts the tool definition and the tool rounds. The TP-SEC-006 engine does the same with tools on. Then `config_read` returns the tool definition, and the static inspection (M5) reads it. The `not_in_run` line on tool schema detail says that the model gets the definition. It also says that the scorer compares each reply with the prompt only. A TP-SEC-001 baseline log with tools off does not match a TP-SEC-006 run with tools on.
- `tests/test_srd1_tools.py` tests the client, the loop, C-07, C-09 and C-18. It also tests the settings, the header and a signed run with tools on. `tests/test_mcp_emulator.py` adds the handler and store tests.

A deployed agent offers none of that to an outside client. `faias_harness/engine/external.py` is a client of the agent's channel. The probe, the `yes` prompt, the lock before the first item and the signature work as for SRD-1.
- Settings `kind: external` (`faias_harness/settings.py`, `targets/examples/external_settings.yaml`). They have no provider, routing locks or token prices, because the harness does not make the agent's model calls. The budget is `cap_usd` and the operator's estimate `cost_per_call_usd`. The run stops before it passes floor(cap / cost) calls, or `max_calls` if lower. Every attempt that may reach the agent is charged. Also `min_interval_ms` (pacing), `reply_timeout_s` and `max_consecutive_errors`. Evidence mode needs the declared model, the declared target version and the M4 value with its reason. A settings file for SRD-1 may now say `kind: srd1`. Its settings hash is unchanged.
- Run log schema 3 (`faias_harness/engine/runlog.py`). The header has `target`, `model` with `pinned: false`, and `budget`. `target` gives the adapter, the channel, the endpoint host, what the channel shows, and the profile name and hash. It also gives the declared model and version with the basis "declared by the operator in the settings; not observed by the harness". `not_in_run` lists what an external run cannot see. `verify` checks these fields. It checks schema 1 and 2 logs as before.
- Channel adapters (`faias_harness/adapters/`). `directline` is for Direct Line 3.0, with a secret or a token endpoint. It is written for Copilot Studio agents and Azure Bot Service bots. `openai-responses` is for the Responses API. It is written for OpenAI, and for Azure AI Foundry agents through a project's Responses endpoint. `a2a` is for Agent2Agent JSON-RPC 1.0 and 0.3. Each offers `conversation` only. `adapters/registry.py` lists them. `adapters/base.py` holds the shared base class, the call budget and the retry rule (HTTP 429 and 503 only).
- `json-http` (`faias_harness/adapters/json_http.py`, `targets/examples/json_app.yaml`) is for a firm's own chat endpoint that takes and returns JSON. It is set up with settings only. They are a request template with `{message}` and `{session_id}`, a reply path, and optional paths. The template is filled in the parsed body, in one pass. Thus the message cannot change the JSON structure or be filled again. The optional paths are for the server's session ID, a block, its type, the model and the finish reason. Fixed headers may hold no key. Tested against a local stand-in only.
- The key header of `generic-http`, `openai-responses` and `a2a` may now be any header name (for example `Ocp-Apim-Subscription-Key`). The scheme defaults to Bearer for Authorization and none for any other header.
- `generic-http` now sends through the egress client. Before, it called the endpoint with the standard library, outside the allow-list. It reads the finish reason, the model named in the response and the token use. It has a test against a local stand-in.
- Profile field `adapter_options` (optional) holds the settings of a channel adapter, and the adapter checks them. A field name from a fixed list of key-like names is refused anywhere in it.
- The profile validator refuses an `endpoint` with a query string, because a query can hold a key. `openai-responses` takes its query from `adapter_options.query`.
- With external settings, the preflight prints the adapter, the endpoint host and what the channel shows. It also prints the declared model and version and the calls against the call budget. It says whether the key variable is present. `--probes` makes one channel probe (one benign message). The probe reaches the firm's agent, so it needs the attestation file. `--start` also needs the M4 value with its reason, so that `verify` accepts the log. It refuses if the probe gets no usable reply. It refuses `--positive-control`, because the harness cannot weaken a deployed agent. The estimate counts the Direct Line start event as a call.
- MCP tool emulator (`faias_harness/emulators/mcp_tools.py`, `targets/examples/mcp_tools.yaml`). It is a server on the local machine that answers MCP requests. It answers protocol version 2026-07-28, with per-request metadata, where the header and the body must match. It also answers 2025-03-26, 2025-06-18 and 2025-11-25, with initialize and a session. It offers tools only, with fixed synthetic results, and writes a hash-chained ledger of every tools/call, refused calls included. It refuses an Origin that is not allowed. With a key variable set, it also refuses a request without the key. It makes each refusal from the headers alone, and closes the connection. Idle connections time out after 15 seconds. At most 256 legacy sessions are kept. A firm points its staging agent's tool at it through a tunnel that the operator runs. No engine uses it yet.
- This release adds the example profiles `targets/examples/copilot_studio.yaml`, `responses_agent.yaml`, `a2a_agent.yaml` and `json_app.yaml`.
- New tests are in `tests/test_adapters.py`, `tests/test_external.py` and `tests/test_mcp_emulator.py`. `tests/standins.py` holds local stand-ins for Direct Line, the Responses API, an A2A agent and an in-app JSON endpoint. `tests/run_all.py` step 4 checks the external example profiles and settings.
- In the Inspect log, a no-result run now has the score kind `no_result`, as in the run log. A no-result run is an empty or cut-off reply, or a channel error. This holds for SRD-1 runs and external runs. Before, the Inspect log scored it as a defence. The signed run log and its measures never used the Inspect score.
